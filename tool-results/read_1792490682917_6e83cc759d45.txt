    19→## 2. First Principle: Inspect Everything Before Changing Anything
    20→
    21→Before modifying a single component, fully investigate the existing application.
    22→
    23→Do not immediately begin adding gradients, changing CSS, installing libraries, replacing components, or rewriting entire files.
    24→
    25→First understand what already exists, how it works, and which parts are already well designed.
    26→
    27→### 2.1 Perform a complete repository audit
    28→
    29→Inspect the available project source code and identify:
    30→
    31→- The frontend framework and architecture.
    32→- The application entry point and routing configuration.
    33→- Every existing screen, page, route, and major component.
    34→- Shared layouts, reusable components, and design-system files.
    35→- Global CSS, component styles, utility classes, and theme definitions.
    36→- CSS variables, color tokens, gradients, shadows, borders, radii, and spacing rules.
    37→- Typography, font loading, icon libraries, and asset usage.
    38→- Liquid Glass styling and backdrop effects.
    39→- Existing transitions, animations, hover effects, and touch interactions.
    40→- Mobile-specific styles, breakpoints, viewport handling, and WebView behavior.
    41→- Chat interfaces, AI input areas, chat history menus, tabs, and conversation views.
    42→- API integration, loading states, asynchronous behavior, and error handling.
    43→- Any existing console errors, framework warnings, failed network requests, or rendering problems that can be observed.
    44→- Repeated CSS declarations, conflicting styles, duplicated components, and inconsistent design patterns.
    45→- Existing performance optimizations and possible regressions.
    46→
    47→Search the entire codebase, not just the homepage or the most visible components.
    48→
    49→Identify which styles are global and which are local. Determine whether different pages use separate layout systems, independent background declarations, different theme wrappers, or inconsistent component implementations.
    50→
    51→Do not assume that a component is broken merely because its code looks unusual. Verify its behavior and understand its purpose first.
    52→
    53→### 2.2 Inspect the running application
    54→
    55→When a working browser, preview, or debugging environment is available, inspect the actual application rather than relying exclusively on source code.
    56→
    57→Visit every accessible route and inspect each page under relevant states.
    58→
    59→Examples include:
    60→
    61→- Initial loading.
    62→- Normal content loaded.
    63→- Empty content.
    64→- API loading.
    65→- API errors.
    66→- Selected and unselected tabs.
    67→- Open and closed menus.
    68→- Open dialogs and bottom sheets.
    69→- Expanded and collapsed components.
    70→- Switching between existing and new chats.
    71→- Long messages and long AI responses.
    72→- Keyboard open and closed.
    73→- Scrolling near the top, middle, and bottom of long pages.
    74→- Switching between screens repeatedly.
    75→- Returning to a screen after navigation.
    76→
    77→Test the app at representative mobile dimensions, particularly narrow phone screens and common Android WebView sizes. Also check desktop or wider layouts wherever the existing app supports them.
    78→
    79→If a browser preview or device simulator is not available, inspect the source thoroughly and explicitly identify which visual or runtime behaviors remain unverified.
    80→
    81→Do not claim to have tested a screen you have not actually accessed.

    83→### 2.3 Create an audit report
    84→
    85→Before making changes, summarize:
    86→
    87→1. What is already working well.
    88→2. What visual inconsistencies exist.
    89→3. What functional bugs or interaction glitches exist.
    90→4. What parts of the design system are inconsistent.
    91→5. Which screens have the largest quality gaps.
    92→6. What might be affecting performance.
    93→7. Which fixes are low risk and which require extra caution.
    94→8. Which files and components are likely responsible for each issue.
    95→
    96→Prioritize actual, observed problems over speculative redesign ideas.
    97→
    98→Then create an ordered implementation plan and begin executing it in controlled stages. Do not stop after producing a report if the code can be modified and tested in the available environment.

   159→## 4. Premium Surface Design: Borderless, Seamless, and Refined
   160→
   161→One of the most important requirements is improving how cards, boxes, panels, and content groups look throughout the application.
   162→
   163→Some cards or boxes may currently appear too ordinary, outlined, harsh, separated, or visually disconnected from the rest of the interface.
   164→
   165→Inspect them individually and improve them where necessary.
   166→
   167→### 4.1 Eliminate unnecessary visible card borders
   168→
   169→For ordinary content cards and panels, the default design direction should be **seamless and visually borderless**, inspired by high-quality Apple interface design.
   170→
   171→Where the existing design uses or would benefit from a borderless treatment:
   172→
   173→- Remove unnecessary visible one-pixel outlines.
   174→- Avoid default gray borders around every card.
   175→- Avoid harsh separators that fragment the interface.
   176→- Create depth with carefully controlled surfaces, soft gradients, subtle shadows, and lighting.
   177→- Use spacing and visual grouping to communicate structure.
   178→- Maintain sufficient contrast between content and its surrounding background.
   179→- Ensure neighboring surfaces blend naturally into the overall interface.
   180→
   181→Do not simply remove all borders mechanically. Preserve separators, focus rings, selected states, and other outlines when they are necessary for usability, accessibility, or clear interaction feedback.
   182→
   183→The objective is to remove visual clutter, not remove useful interface information.
   184→
   185→### 4.2 Improve surface quality
   186→
   187→Examine the existing cards and determine the most appropriate treatment for each.
   188→
   189→Potential treatments include:
   190→
   191→- Soft, low-contrast surface gradients.
   192→- Subtle gold-tinted highlights.
   193→- Carefully controlled translucent surfaces.
   194→- Gentle ambient shadows.
   195→- Refined edge lighting where appropriate.
   196→- Subtle differences in surface brightness.
   197→- Better corner radii and proportional padding.
   198→- Cleaner relationships between cards and backgrounds.
   199→- More deliberate spacing between grouped elements.
   200→
   201→Choose treatments based on the existing component, its purpose, and the active feature's theme.
   202→
   203→Do not apply every visual effect to every component.
   204→
   205→Some components should remain visually quiet. Others may deserve a more expressive appearance.
   206→
   207→The overall interface should feel like a coherent premium product rather than a collection of independently decorated cards.
   208→
   209→### 4.3 Apply gradients with restraint
   210→
   211→Use gradients derived from the established brand palette.
   212→
   213→For example, gold-to-warm-white, subtle gold-to-transparent, or appropriate feature-specific accent gradients may work well for certain components if they fit the existing visual identity.
   214→
   215→Use rose, burgundy, or emerald accents where the feature or tab already uses those colors.
   216→
   217→Gradients should be smooth, sophisticated, and controlled. Avoid overly saturated fills, rainbow effects, excessive multicolor gradients, or combinations that make the interface look cheap.
   218→
   219→Do not give every box the same strong gold gradient.
   220→
   221→Vary the treatment according to component hierarchy, existing theme, content importance, and the page background.
   222→
   223→Gradients should enhance the app's design, not compete with its content.
   224→
   225→### 4.4 Preserve visual hierarchy
   226→
   227→Keep the distinction between primary actions, secondary actions, supporting information, and background content clear.
   228→
   229→Do not make every button, card, or heading equally prominent.
   230→
   231→Use stronger treatments for important actions and quieter treatments for supporting elements.
   232→
   233→The final result should feel premium because of its restraint, precision, consistency, and attention to detail—not because every component has multiple effects.

   603→## 10. Performance Is a Core Requirement
   604→
   605→The visual refinement must not make the application slower.
   606→
   607→The app runs through an existing web frontend and mobile WebView, and its service is hosted on Render. Avoid adding unnecessary client rendering work, network traffic, heavy assets, libraries, or backend requests.
   608→
   609→Understand which work happens on the user's device and which happens on the server.
   610→
   611→Purely visual CSS effects generally affect client-side rendering; they should not be moved onto the backend merely because the service is hosted on Render. Nevertheless, unnecessary requests, oversized payloads, repeated API calls, server-side rendering regressions, or inefficient backend operations can affect overall responsiveness.
   612→
   613→### 10.1 Performance audit
   614→
   615→Investigate:
   616→
   617→- Slow screen transitions.
   618→- Excessive component re-rendering.
   619→- Long JavaScript tasks.
   620→- Unnecessary event listeners.
   621→- Repeated API requests.
   622→- Duplicate network calls on navigation.
   623→- Layout shifts.
   624→- Excessive DOM complexity.
   625→- Expensive filters and backdrop blur.
   626→- Repeated animations.
   627→- Memory leaks.
   628→- Event handlers not cleaned up when components unmount.
   629→- Large image or font assets.
   630→- Unnecessary dependencies.
   631→- Excessive timers, polling, or retry loops.
   632→- Slow list rendering.
   633→- Lag during scrolling or swiping.
   634→- Slow keyboard and input interactions.
   635→- Resource loading problems.
   636→
   637→Only claim a performance issue is confirmed when it is supported by profiling, measurements, or reproducible behavior.
   638→
   639→### 10.2 Optimize visual effects carefully
   640→
   641→When introducing or refining transitions and gradients:
   642→
   643→- Prefer transform and opacity animations when they reproduce the desired effect.
   644→- Avoid animating properties that repeatedly trigger expensive layout calculations where possible.
   645→- Avoid perpetual animations that offer no meaningful user benefit.
   646→- Avoid adding multiple expensive blur layers to every card.
   647→- Limit unnecessary repaint areas.
   648→- Load fonts and assets efficiently.
   649→- Avoid adding large animation libraries for minor effects.
   650→- Respect reduced-motion preferences where supported.
   651→- Keep touch interactions responsive during animations.
   652→
   653→Do not sacrifice a signature premium effect without first exploring an efficient implementation.
   654→
   655→### 10.3 Verify performance
   656→
   657→Use the available browser, device, and profiling tools to compare behavior before and after the changes.
   658→
   659→Check for regressions in:
   660→
   661→- Initial loading.
   662→- Navigation.
   663→- Scroll smoothness.
   664→- Button response.
   665→- Chat switching.
   666→- Text input.
   667→- Rendering large responses.
   668→- API-related loading states.
   669→
   670→When supported, capture measurable before-and-after results. If the required profiling tools are unavailable, state that performance has not been conclusively measured.
   671→
   672→Do not assume that fewer lines of code necessarily means better performance.
   673→

   675→
   676→## 11. Find and Fix Functional Bugs Without Rewriting the App
   677→
   678→Perform a complete debugging pass alongside the visual review.
   679→
   680→Inspect for:
   681→
   682→- JavaScript or framework exceptions.
   683→- Console warnings with meaningful impact.
   684→- CSS errors and unexpected overrides.
   685→- Invalid component state transitions.
   686→- Broken navigation.
   687→- Buttons that do not work.
   688→- Duplicate event handlers.
   689→- Unhandled promises.
   690→- Requests that fail silently.
   691→- Invalid or incomplete API responses.
   692→- Stale data after navigation.
   693→- Incorrect loading-state transitions.
   694→- Forms that submit multiple times.
   695→- Unintended full-page refreshes.
   696→- Menus that remain open.
   697→- Overlays that block further interactions.
   698→- Lost scroll position when it should be preserved.
   699→- Race conditions between network requests.
   700→- Components rendering stale state.
   701→- Chat data appearing in the wrong conversation.
   702→- Backgrounds or theme state changing after navigation.
   703→- Inconsistent styling after returning from another screen.
   704→
   705→For each reproducible issue:
   706→
   707→1. Identify the affected screen or component.
   708→2. Record how to reproduce the issue.
   709→3. Find the probable root cause.
   710→4. Confirm it with the available evidence.
   711→5. Implement the smallest safe fix.
   712→6. Retest the affected flow.
   713→7. Test nearby screens and shared components for regressions.
   714→
   715→Do not indiscriminately refactor working systems just because you noticed an opportunity to change them.
   716→
   717→Prefer minimal, targeted, well-validated changes unless a deeper architectural problem makes a broader fix necessary.

   721→## 12. Preserve the Existing Backend and Business Logic
   722→
   723→This task is primarily about frontend quality, UI consistency, interaction behavior, and WebView reliability.
   724→
   725→Do not change the backend architecture simply to implement styling improvements.
   726→
   727→Preserve the current API contract and all existing calculation logic. Do not move calculations into the frontend or replace server responses with demo data.
   728→
   729→Do not introduce additional API requests solely for decorative UI behavior.
   730→
   731→If a frontend bug is caused by incorrect API handling, investigate the interaction and make the smallest correct fix without changing server-side business rules unnecessarily.
   732→
   733→If a backend change is genuinely required, explain why, determine its impact, and keep it separate from unrelated visual refinements.
   734→
   735→Do not expose private credentials or weaken authentication while debugging.

   739→## 13. Do Not Redesign Everything
   740→
   741→This requirement overrides any temptation to start over.
   742→
   743→**Keep the existing layout structure, established visual language, brand colors, important design decisions, and working features unless there is a demonstrated reason to change them.**
   744→
   745→Specifically:
   746→
   747→- Do not replace the whole application theme.
   748→- Do not change every card just for visual novelty.
   749→- Do not invent a new navigation system.
   750→- Do not change the application's information architecture.
   751→- Do not remove features to simplify the design.
   752→- Do not rebuild components that already work well without a clear benefit.
   753→- Do not replace the typography system unnecessarily.
   754→- Do not introduce unrelated colors or gradients.
   755→- Do not install unnecessary UI libraries.
   756→- Do not make the entire app look identical if specific features intentionally use different established accents.
   757→- Do not introduce excessive animations or decorative elements.
   758→- Do not make sweeping CSS replacements without understanding their scope.
   759→- Do not apply global overrides as a shortcut for fixing individual components.
   760→- Do not overwrite working application logic with a generic template.
   761→
   762→Keep approximately the same visual identity, interaction model, and screen structure.
   763→
   764→Improve the areas that are inconsistent, unfinished, buggy, or visibly below the quality of the app's best-designed components.
   765→
   766→A successful result should look like a more polished version of the same application—not an entirely new product.

   806→Fix the conversation background inconsistency at its root.

   808→Refine the chat composer, history menu, message surfaces, loading states, transitions, keyboard behavior, and switching between conversations.

   811→

   814→Make button feedback, tabs, page transitions, swipes, drawers, and overlays consistent.
   815→

   820→Test layouts, safe areas, keyboard behavior, scroll interactions, and fixed elements on supported device dimensions.

   826→Investigate whether the changes cause additional work, expensive rendering, network traffic, or memory usage.

   831→
   832→Retest all routes and important user journeys.
